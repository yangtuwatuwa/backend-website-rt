# Kas RT manual: tutup buku dan saldo berkelanjutan

Modul ini memakai `kas_transaksi`. Saldo tidak disimpan di setiap transaksi. Tutup buku menyimpan snapshot resmi dalam `kas_periode_tutup_buku`; seluruh transaksi asli tetap tersedia untuk laporan.

## Migrasi dan pengaktifan

Untuk database yang sudah memiliki `kas_transaksi`, jalankan migrasi tambahan sebelum menjalankan kode baru:

```sh
npm run migrate:kas-tutup-buku
```

Migrasi dapat dijalankan ulang. Migrasi membuat tabel snapshot dan `kas_buku_lock` dengan satu baris untuk mengurutkan penutupan serta perubahan transaksi yang datang bersamaan, termasuk ketika belum ada penutupan pertama. Tidak ada reset atau penghapusan data. Setup database test menggunakan skema kanonis yang sudah mencakup kedua tabel ini.

## Menutup periode

`POST /admin/finance/kas-transaksi/tutup-buku`

JWT wajib. Role yang diizinkan: `bendahara`, `rt`, `superadmin`. Role `admin` dan `sekertaris` tidak dapat menutup buku. Pembatasan memakai `checkRoles` yang sudah ada dan diperiksa kembali oleh service.

```json
{
  "periode_selesai": "2025-12-31",
  "keterangan": "Tutup buku tahun 2025"
}
```

- `periode_selesai` opsional, default tanggal hari ini di `Asia/Jakarta`; alias `tanggal_cutoff` diterima. Tanggal cutoff termasuk dalam periode yang ditutup. Tanggal masa depan ditolak.
- `keterangan` opsional, maksimal 2000 karakter.
- `periode_mulai` dihitung server: sehari setelah cutoff terakhir, atau tanggal transaksi aktif paling awal sampai cutoff untuk penutupan pertama. Jika belum ada transaksi sampai cutoff, awal periode sama dengan cutoff. Jika dikirim klien, nilainya wajib cocok dengan hasil tersebut.
- Penutupan pertama memiliki `saldo_awal = 0`. Penutupan berikutnya mengambil `saldo_akhir` dari penutupan aktif terakhir. Periode kosong boleh ditutup dan meneruskan saldo yang sama.
- Semua total dihitung server dengan SQL DECIMAL. Nilai saldo/total yang dikirim klien diabaikan. Snapshot dan audit `KAS_PERIOD_CLOSED` disimpan dalam satu transaksi; kegagalan audit membatalkan penutupan.
- Tidak boleh ada duplikasi, rentang tumpang tindih, atau celah setelah penutupan terakhir.

Respons `201` mengikuti pembungkus Kas RT yang sudah ada:

```json
{
  "response": 201,
  "output": {
    "pesan": {
      "id": 2,
      "periode_mulai": "2025-01-01",
      "periode_selesai": "2025-12-31",
      "saldo_awal": 500000,
      "total_pemasukan": 1000000,
      "total_pengeluaran": 250000,
      "saldo_akhir": 1250000,
      "jumlah_transaksi": 20,
      "ditutup_oleh": 7,
      "ditutup_role": "bendahara",
      "ditutup_pada": "2026-01-01T03:00:00.000Z",
      "keterangan": "Tutup buku tahun 2025"
    },
    "token": null
  },
  "message": "Periode Kas RT berhasil ditutup."
}
```

Record juga menyertakan kolom audit standar `created_by`, `updated_by`, `deleted_by`, `created_at`, `updated_at`, `deleted_at`. Penutupan yang berhasil memicu event sinkronisasi `finance`.

## Riwayat tutup buku

`GET /admin/finance/kas-transaksi/tutup-buku?page=1&limit=25`

Menggunakan role baca Kas RT yang sudah ada: RT, sekretaris, bendahara, superadmin, admin. `output.pesan` berisi `{ data: [...snapshot], pagination: { page, limit, total, total_pages } }`. Urutan cutoff terbaru dahulu; limit 1–200. Record soft-deleted dikecualikan. Setiap snapshot menyimpan saldo awal/akhir periodenya sendiri dan tetap sama setelah penutupan berikutnya.

## Perubahan kontrak ringkasan dan laporan untuk FE

`GET /admin/finance/kas-transaksi/summary` tanpa filter tanggal menampilkan periode berjalan:

```text
saldo_awal        = saldo_akhir penutupan aktif terakhir (atau 0)
total_pemasukan   = pemasukan setelah cutoff terakhir
total_pengeluaran = pengeluaran setelah cutoff terakhir
saldo_akhir       = saldo_awal + total_pemasukan - total_pengeluaran
jumlah_transaksi  = jumlah transaksi setelah cutoff terakhir
```

**Field baru: `saldo_awal`** pada ringkasan dashboard, `summary` laporan bulanan/tahunan/rekap, dan ringkasan ekspor. FE perlu menampilkannya agar saldo akhir tidak disalahartikan sebagai selisih pemasukan/pengeluaran periode saja. Penutupan tidak membuat uang hilang: setelah tutup buku tanpa transaksi baru, pemasukan/pengeluaran periode menjadi 0, tetapi saldo akhir tetap sama.

Ringkasan dengan filter tanggal eksplisit (`tanggal_mulai`/`tanggal_selesai`, alias camelCase atau `date_from`/`date_to`) menghitung rentang historis tersebut. Saldo awal adalah saldo sebelum tanggal mulai; saldo akhir menambahkan arus kas rentang itu. Jika tanggal mulai tidak diberikan, seluruh awal riwayat digunakan dan saldo awal 0. Perubahan ini juga berlaku ketika belum ada penutupan.

Laporan `/laporan/bulanan`, `/laporan/tahunan`, `/laporan/rekap` selalu memakai rentang laporannya sendiri, tanpa cutoff terbaru. `months[]` pada laporan tahunan menambahkan `saldo_awal` dan `saldo_akhir` untuk tiap bulan; field `saldo` tetap merupakan arus kas bersih bulan tersebut. Bulan tanpa transaksi meneruskan saldo sebelumnya.

Filter kategori, keyword, atau tipe mutasi menghasilkan subtotal transaksi, dengan `saldo_awal = 0`, supaya saldo global tidak tercampur dengan sebagian transaksi. FE harus menampilkan hasil filter tersebut sebagai subtotal, bukan jumlah uang kas keseluruhan. Pada rincian tahunan yang difilter, saldo awal/akhir bulan menggambarkan akumulasi subtotal sejak awal tahun.

Ekspor `/export` dan `/cetak` memakai seluruh transaksi pada rentang yang diminta, termasuk seluruh riwayat jika tidak ada filter tanggal. Ringkasannya sesuai dengan rentang ekspor dan mencantumkan saldo awal; ekspor tidak memakai batas periode berjalan dashboard. Daftar transaksi juga tetap dapat menampilkan seluruh riwayat.

Dashboard `/post/dashboard-stats` dan `/admin/finance/summary` menggunakan modul `financial_ledger` yang terpisah. Kontrak tutup buku di sini berlaku untuk endpoint `kas-transaksi` di atas; tidak menggabungkan kedua sumber kas tersebut.

## Perlindungan periode tertutup dan error

Setelah tutup buku, service menolak transaksi baru bertanggal pada/sebelum cutoff, perubahan atau penghapusan transaksi periode tertutup, serta pemindahan transaksi periode terbuka ke periode tertutup. Perubahan transaksi periode terbuka tetap tersedia. Ini menjaga laporan historis dan snapshot tetap sejalan. Koreksi periode lama harus dilakukan sebagai transaksi penyesuaian di periode terbuka dengan keterangan yang jelas.

| Status | Code | Arti |
| --- | --- | --- |
| 403 | `KAS_CLOSING_FORBIDDEN` | Role service tidak berhak menutup buku; route guard juga dapat langsung mengembalikan 403 sesuai format RBAC lama |
| 409 | `KAS_CLOSING_OVERLAP` | Cutoff/rentang bertumpang tindih atau mundur |
| 409 | `KAS_PERIOD_CLOSED` | Transaksi berada dalam periode tertutup |
| 400 | `KAS_CLOSING_START_MISMATCH` | Awal periode tidak sesuai hasil server |
| 400 | `KAS_FUTURE_CLOSING` | Cutoff di masa depan |
| 400 | `INVALID_DATE`, `INVALID_DATE_RANGE`, `FIELD_TOO_LONG`, `INVALID_PAGINATION` | Input tidak valid |

Soft-delete dan kolom audit tersedia untuk kebutuhan pembatalan di masa depan. Tidak ada endpoint undo/override dalam fitur ini; pembatalan memerlukan alur tersendiri yang menjaga urutan penutupan dan audit.

## Verifikasi

```sh
npm test -- --runInBand tests/services/kasPeriodClosingService.test.js tests/services/kasTransaksiService.test.js
```

Suite menggunakan database test terpisah, executor yang di-rollback per test, dan savepoint service. Skenario concurrency memakai dua koneksi InnoDB nyata dan membersihkan fixture yang dikomit berdasarkan ID-nya. Cakupan meliputi snapshot pertama/berikutnya, periode kosong, carry-forward dan pecahan/negatif, cutoff inklusif, RBAC, validasi rentang, audit/rollback, integritas transaksi, laporan historis, ekspor, dan permintaan bersamaan.
